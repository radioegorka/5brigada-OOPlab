# Authorization: справка по объектам

Здесь описаны данные и методы сервиса. Нужные изменения для ЛР1 перечислены в [TASK.md](TASK.md).
Часть методов уже реализована в заготовке, остальные добавляются по мере выполнения работ.

## Данные и поведение

Авторизация получает результаты уже выполненных проверок и формирует решение о возможности покупки. Она не списывает деньги и не обращается к другим сервисам.

`AuthorizationRequest(transaction_id, checks)` содержит ровно шесть `NamedCheck(name, result)`: `CUSTOMER`, `CARD`, `MERCHANT`, `FUNDS`, `LIMITS`, `FRAUD`. Порядок входных проверок сохраняется. Классы `NamedCheck` и `CheckResult` уже готовы.

| Результат | `approved` | `reason` | `failed_codes` |
|---|---|---|---|
| Разрешение | `True` | `None` | Пустой `tuple`. |
| Отказ | `False` | Непустой код причины. | Непустой `tuple`; первый элемент совпадает с `reason`. |

Общий интерфейс — `AuthorizationRule.decide(request) -> AuthorizationResult`. `FirstFailureRule` выбирает первый отказ во входном порядке, `PriorityFailureRule` — первый по приоритету: `CUSTOMER`, `CARD`, `MERCHANT`, `FRAUD`, `LIMITS`, `FUNDS`. Этот же приоритет использует `CollectFailuresRule`.

`AuthorizationService.authorize(request)` вызывает выбранную реализацию. Готовая проверка результата не позволяет одобрить запрос с отказами или вернуть причину, которой нет во входных данных. Риск и достаточность средств повторно не рассчитываются.

## Работа с готовым кодом

Обращение к сервису выполняется через `app/api.py`. Разрешённые файлы указаны в [TASK.md](TASK.md).
Проверки используют подготовленные данные и не зависят от работы других групп.

Функции `create`, `make`, `call` и `view` связывают готовый API с реализацией. Используемые ими функции сервисного модуля должны сохранять сигнатуры. Сам `app/api.py` не редактируйте.

До ЛР5 сборка предоставлена готовой. Нужные объекты могут создаваться в сервисном модуле; `assembly.py` менять не нужно.

Метод сервиса — `authorize(request)`. В ЛР6 стандартная сборка использует `CollectFailuresRule`.

## Ошибки и результаты

`DomainError` содержит код ошибки. При отказе проверки состояние объекта не должно меняться.
Ошибка переданной зависимости не заменяется успешным результатом. Конкретные коды и примеры
приведены в задании и открытых тестах.
